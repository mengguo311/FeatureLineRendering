# 主协议后追加的 DEV 墨量匹配诊断

这项追加诊断不属于主协议四臂。主协议的加宽半径上限未能达到目标 DEV 墨量，因此原始匹配误差保留；另冻结 `PROTOCOL_MATCHED_INK_AUDIT.json`，仅扩大同一个历史 A 图的固定世界半径，检验“更多墨量”这一混杂因素。未修改主多源模型、选核、宽度选择、科学门槛、主资产、主八视角板或历史结论。

每场景从原 tube 半径开始倍增，最大为已封存主 mesh 包围盒对角线的一半；找到均值墨量区间后执行 12 次二分，从所有真实 trials 中选最接近目标者。唯一拟合数据为预先冻结的四个 DEV 相机。追加资产各自封存后才由追加脚本读取 reserved RGB/alpha 并评估；这些相机已经由主实验使用，不称新的盲测。

实际查看了两场景完整八行追加对照预览，并查看 Lego r_1、Chair r_14 的原尺寸四列对照。主 multi24 的外形和部件相对位置更接近原 RGB；同墨量旧 A 的加宽无法补足原两源没有的结构，且出现膨大的管段、孤立团块、错误位置和后方穿体线。Lego 主结果的车体、挖斗与驾驶室出现大片实黑；Chair 主结果的靠背和坐面也大量填黑，多数视角接近剪影。这些外观和深内部墨量统计不支持“干净宽轮廓带成功”。追加控制揭示粗管本身不能替代更多形体支持，也不能把主方法的实心化代价忽略掉。

所有图均真实投影固定实体三角面，只使用资产自身 z-buffer；相对原 GS 物体仍是 x-ray，后方区域没有人为隐藏。追加结果没有作为主科学门槛的救援或替换。

首轮脚本在主旧图加宽资产的 hash 检查处停止：主记录使用导出前 int64 faces 的字节 hash，导出 NPZ/GLB 使用 int32 索引。两场景主 multi24 hash 均直接一致；旧图加宽 faces 转回 int64 后与原记录精确匹配，索引数值和顶点没有变化。失败 traceback 保留在每场景 `FAILURE_ATTEMPT_01.json`；追加脚本显式记录这两种 hash，自己的追加资产统一使用 float32 vertices / int32 faces。没有重写主记录掩盖该工程问题。

`PRIMARY_PROTECTED_AFTER.json` 证明本次检查的 44 个主协议、资产、seals、主拼图文件 hash 不变。完整 trials、几何 hash、四个 DEV 逐图计数和导出路径在 `results/<scene>_post_protocol_dev_ink_diagnostic_asset.json`；每场景的全部八视角指标在 `ADDITIONAL_METRICS.json`，独立原尺寸与预览板在 `reserved_eight_additional_FULL.png` / `reserved_eight_additional_preview.jpg`。
